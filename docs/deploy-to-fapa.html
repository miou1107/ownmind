OwnMind 換一台伺服器

OwnMind 現在跑在 kkvin 那台個人小機器上。這份文件講的是把它換到公司 FAPA 的測試機跟正式機， 以及大家的記憶怎麼跟著過去。

Vin 從頭讀，伺服器規格那節可以跳過。看完只剩一個時段要挑。 Eric 前三節看全貌，你要動手的地方在「Eric 出場三次」跟「伺服器規格」。

記憶擺到最後才動，前面做壞了都還能回頭

程式碼跟資料是兩件事，分兩趟走。兩趟之間隔一週或隔一個月都不影響。

GitLab 那一份是副本，不是搬家

FAPA 的自動部署只認公司 GitLab 上 Projects/ 底下的專案。伺服器要進得了這個環境，程式碼就得有一份在那裡。

GitHub 仍然是唯一的開發跟發布來源，使用者的安裝跟升級路徑一個字都不會改。副本只在打 tag 的時候同步一次，平常 push 不同步，公司的建置清單不會被塞滿。GitLab 上也不帶完整歷史，每次同步是一個 sync v1.x.x 提交，這是 FAPA 規範 id=422 的要求。

Eric 出場三次

  1. 核准登記單 程式碼第一次推上 GitLab 會被 CI 擋下，機器人自動開一張登記單指派給 Eric。核准之後，機器人會自己產生 ci/ownmind/.gitlab-ci.yml 骨架。
  2. 補 CI 檔裡的 TODO 測試指令、部署路徑、健康檢查網址這四項，整理好的內容在下面的伺服器規格那節。
  3. 兩台機器上的設定檔與網站掛載 ownmind.env 放進 /opt/deploy/envs/，網站設定加一段 /ownmind/。這一段照理歸運維，由 Eric 做或他授權 Vin 做都可以，兩位談定就好。

第二趟怎麼走

這一趟才會停機。停機期間所有人存記憶、搜記憶會失敗，Claude 本身照常。

記憶用一支腳本搬，不用手動接指令

倉庫裡有 scripts/migrate-to-fapa.sh，在自己電腦上跑，它自己連到兩台機器，不用先登進去。三個指令：

bash scripts/migrate-to-fapa.sh check 兩邊連不連得上、各有幾筆記憶、磁碟還剩多少。什麼都不動，事前先跑這個。
bash scripts/migrate-to-fapa.sh cutover 停掉舊機器、匯出、傳過去、匯入、比對筆數。筆數對不上就停在那裡不往下走，並且叫你退回。
bash scripts/migrate-to-fapa.sh rollback 把舊機器開回來。舊機器上的資料一筆都沒刪，所以退回是幾秒鐘的事。

正式那天之前先拿測試機演練一次，同一支腳本換一個目標：DST_HOST=root@test-fapa.welcometw.com bash scripts/migrate-to-fapa.sh cutover。

舊機器那一步是整個停掉，不是切成唯讀，因為 OwnMind 沒有唯讀模式。匯出的時候還有人在寫，會漏掉幾筆而且不會有人發現。

退回要留意的只有一個窗口：已經有人往新機器寫入之後才退回，那幾筆新記憶得手動補回來。

收尾，不趕時間

出一版 OwnMind，讓使用者升級時自動把位址改成 fapa；用管理後台廣播提醒大家升級；看活動紀錄還有誰在走舊位址。全部人都換過去大約要兩到四週，之後就能關掉 kkvin 的轉送。

3100 這個埠在兩台機器上都沒有被佔用。實測占用 api 約 42 MB、db 約 200 MB，合計約 250 MB。

部署方式

沿用 FAPA 現行專案那一套，沒有特殊需求：原始碼 rsync 到 /opt/deploy/ownmind/，軟連結 /opt/deploy/envs/ownmind.env，docker compose build 之後換版。只重建 api 一個服務就好，db 用官方映像不需要重建。建置要加 --no-cache，含前端編譯大約 90 秒到 2 分鐘。

軟連結的落點要放在 compose 專案目錄下、名字就叫 .env（也就是 /opt/deploy/ownmind/.env）。docker-compose.yml 裡資料庫密碼寫成 ${DB_PASSWORD}，那個展開只認 compose 專案目錄的 .env，只掛成 env_file 的話會展開成空字串，postgres 第一次啟動就會失敗。

正式機的加密金鑰由腳本帶過去，不用人工複製

使用者透過 OwnMind 存放的密碼是用 kkvin 上那把金鑰加密的，換成別把就全部解不開。migrate-to-fapa.sh cutover 會在還原資料的同時把那把金鑰寫進正式機的設定檔，並且比對指紋確認寫成功，對不上就中止。正式機設定檔裡先填的那把只是讓服務啟得起來，搬資料前沒有任何東西用它加密過。測試機的資料是另外一份，自己產一把就好。

資料庫遷移與網站設定

db/ 底下的 SQL 由程式啟動時自行套用，不需要人工執行，也不要掛 docker-entrypoint-initdb.d。

網站那邊要在共用的 vhost 檔加一段，兩台都要。內容跟 kkvin 上正在跑的那段一樣：

location = /ownmind {
    return 301 /ownmind/;
}

location /ownmind/ {
    rewrite ^/ownmind/(.*) /$1 break;
    proxy_pass http://localhost:3100;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

前綴要脫掉，程式收到的路徑不帶 /ownmind。後台頁面會依照請求深度自己改寫 base href，脫掉前綴之後靜態檔一樣抓得到。

做法是改動前先備份，驗證通過才套用。設定有錯的時候網站程式會拒絕套用並繼續跑舊設定，其他專案不會斷線。

跟共用同一個倉庫的其他專案會不會互相影響

FAPA 那個倉庫是多人、多專案共用，OwnMind 進去之後同一層還有 ima、ring 那些專案。互相影響的地方只有兩個，其餘都被守門擋住了。

誰做什麼會發生什麼
你把 OwnMind 的程式碼放進去 動不到別的專案目錄。守門只放行自己專案那一層，超出範圍的改動會被擋下來
別人上傳他們自己的專案 同一套守門，碰不到 OwnMind 的目錄
你標記版本要部署 只會部署 OwnMind。版本標記認的是各專案自己的前綴，別人的部署不會被你觸發，你的也不會被別人觸發
你的測試正在跑 會佔用共用的建置機器，同一時間別人的部署可能要排隊。OwnMind 的測試套件不小，這一點還沒實際量過
加上 /ownmind/ 那一段網站設定的時候 全部專案共用同一個設定檔，這是唯一真的會波及別人的地方。設定寫錯的時候網站程式會拒絕套用並繼續跑舊設定，所以不會把別人弄斷線
OwnMind 跑起來以後 跟同一台上的其他服務分記憶體，約 250 MB。埠號 3100 兩台都沒有被佔用
公司裡有這個倉庫權限的人 讀得到 OwnMind 的原始碼。GitHub 那份是對外的來源，公司這份是給伺服器用的副本，兩份內容一樣
