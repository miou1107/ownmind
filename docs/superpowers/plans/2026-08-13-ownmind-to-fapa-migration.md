# OwnMind 搬遷到 FAPA 執行方案

這份文件是 OwnMind 伺服器從 kkvin.com 搬到公司 FAPA 環境的完整執行計畫。
讀完你會知道：搬遷分幾步、每一步做完你會看到什麼、哪裡有停機、出事怎麼退回。
你現在要做的：看完後回答文末的兩個問題，我就照這份計畫動工。

已拍板的三件事（2026-08-13 對話），本計畫以此為前提：

1. 程式碼照舊 push 到 GitHub，由自動同步程式複製到公司 GitLab 並觸發部署
2. 使用者下載安裝仍走 GitHub，GitLab 只為了讓伺服器進 FAPA 環境
3. 所有人的記憶跟著搬

---

## 一、搬完之後的樣子

| 項目 | 現在 | 搬完後 |
|---|---|---|
| 你發版 | push GitHub，SSH 進 kkvin 手動重建 | push GitHub 照舊；要更新伺服器時打一個 tag，剩下全自動 |
| 伺服器 | kkvin.com（你個人的 1GB 小機器） | fapa.welcometw.com（公司正式機，另有測試機可先驗） |
| 服務網址 | `https://kkvin.com/ownmind` | `https://fapa.welcometw.com/ownmind` |
| 使用者裝 / 升級 | GitHub | 照舊，完全不變 |
| 使用者的設定 | 指向 kkvin | 升級一次新版就自動改指向 fapa，過渡期舊位址照樣通 |
| 記憶資料 | kkvin 上的資料庫 | fapa 上的資料庫（9 個使用者、資料庫 285 MB，全部搬） |

附帶的好處：kkvin 那台只有 1GB 記憶體、磁碟已用掉 81%，早就跑得很勉強。搬走後它可以退役或減負擔。

---

## 二、發版以後怎麼運作（搬完後你的日常）

- **你平常 push GitHub**：什麼都不會發生，GitLab 不同步。你一天發好幾版也不會去洗公司的 CI 列表。
- **你想更新測試機**：在 GitHub 打 tag `deploy-rc`（或跑一個指令）。同步程式把當下的程式碼複製一份推到 GitLab 的 `Projects/ownmind/`，打上 `ownmind-rc` 標籤，FAPA 的 CI 自動跑測試、部署到測試機。
- **你確認測試機沒問題、想上正式機**：打 `ownmind-v` 標籤，然後進 GitLab 網頁按一下手動部署按鈕。這是 FAPA 全公司的規矩（正式機一律人手按），我不會也不能自動按。
- **GitLab 那份只是鏡像**：每次同步是一個「sync v1.26.x」的提交，不帶 GitHub 的完整歷史（FAPA 規範要求捨棄舊歷史）。完整歷史永遠在 GitHub。

## 三、執行步驟

### 階段 0：把管線建好（不碰任何正在跑的服務）

依團隊規範（id=412），`ci/` 目錄與主流程檔全歸 Eric 管，Vin 也無權動；規範（id=422）設計的入場方式是「直接 push、讓機器人開單給 Eric」，所以這一段不用任何人手改共用檔：

| # | 做什麼 | 誰做 |
|---|---|---|
| 0-0 | 跑移交規範的前置四關：資安掃描（確認沒有任何密碼金鑰進倉庫）、AI 程式碼審查、測試全綠、Docker 設定確認 | 我 |
| 0-1 | 寫 GitHub Actions 同步程式（GitHub → GitLab，只在打 tag 時跑），權杖存 GitHub 密鑰區 | 我 |
| 0-2 | 第一次把程式碼推到 GitLab 的 `Projects/ownmind/`。CI 會照設計把它擋下，同時**自動開一張登記單給 Eric** | 我推，機器人開單 |
| 0-3 | Eric 核准那張單 → 機器人自動建好 ownmind 的 CI 骨架 | Eric 按一下 |
| 0-4 | 把部署所需細節（測試指令、部署路徑、網址）整理好給 Eric，由他補進 CI 檔 | 我整理，Eric 補 |

完成的判斷：GitHub 打一個測試 tag，GitLab 的 `Projects/ownmind/` 出現程式碼，CI 測試跑綠。

### 階段 1：測試機試跑（still 不碰正式服務）

| # | 做什麼 |
|---|---|
| 1-1 | 在兩台 FAPA 機器的 `/opt/deploy/envs/` 放好 `ownmind.env` 設定檔（新的加密金鑰與密碼，不沿用 kkvin 的明文搬運） |
| 1-2 | 打 rc tag，讓 CI 把 OwnMind 部署到測試機 |
| 1-3 | 從 kkvin 複製一份當天的記憶資料到測試機 |
| 1-4 | 在測試機的網站設定加 `/ownmind/` 這段（先備份、驗證過才套用） |
| 1-5 | 用我自己的帳號連測試機實測：搜記憶、存記憶、鐵律提醒、管理後台，全部真的跑一遍 |

完成的判斷：`https://test-fapa.welcometw.com/ownmind` 開得起來，而且上面那些操作全部實測通過，不是「照理說會過」。

### 階段 2：正式搬遷（有停機，時段等你指定）

這一段預估 15 到 30 分鐘。期間所有人存記憶、搜記憶會失敗，AI 工具本身不受影響（OwnMind 的鉤子斷線時會安靜跳過，不會卡住大家的 Claude）。

| # | 做什麼 | 分鐘 |
|---|---|---|
| 2-1 | 打 v tag、GitLab 按下部署，正式機跑起 OwnMind（先空著） | 事前做完 |
| 2-2 | kkvin 上把 OwnMind 切成唯讀（擋寫入，讀還通） | 1 |
| 2-3 | 資料庫完整匯出（285 MB，含匯出約 2 分鐘）、傳到 fapa、匯入 | 5–10 |
| 2-4 | 核對：兩邊記憶筆數、使用者數、最新一筆的時間戳一致 | 2 |
| 2-5 | 正式機的網站設定加 `/ownmind/`、驗證、套用 | 2 |
| 2-6 | kkvin 的 `/ownmind/` 改成原封不動轉送到 fapa（不是轉址，使用者端完全無感） | 2 |
| 2-7 | 用真帳號在新舊兩個位址各實測一輪 | 5 |

**退回方案**：2-6 之前任何一步出問題，把 kkvin 的唯讀解除就回到原狀，資料零損失。2-6 之後發現問題，把 kkvin 的轉送改回本機服務即可，同樣是幾分鐘的事。唯一要小心的窗口是「已經有人往 fapa 寫入之後才退回」，這種情況新寫入的記憶要手動補搬，所以切換後 48 小時內我會把 fapa 的資料每天備份回 kkvin。

### 階段 3：使用者換位址 + 收尾（不趕時間）

| # | 做什麼 |
|---|---|
| 3-1 | 出一版 OwnMind：升級時自動把設定裡的 kkvin 位址改成 fapa 位址 |
| 3-2 | 用管理後台的廣播功能提醒大家升級 |
| 3-3 | 觀察管理後台的活動紀錄，看還有誰在走舊位址 |
| 3-4 | 全部人都走新位址之後（估 2 到 4 週），關掉 kkvin 的轉送、kkvin 退役或另作他用 |

## 四、風險，講清楚

| 風險 | 實情 | 對策 |
|---|---|---|
| fapa 記憶體吃緊 | 8G 已用 4.5G、備援記憶體用滿。OwnMind 再吃約 0.5–1G，塞得下但更緊 | 部署後盯一週的記憶體曲線；不夠就找 Eric 談加記憶體，這在 Linode 上是升級方案的事 |
| 機器是共用的 | fapa 上還跑著 ima、ring、ai_kol 等服務，7 月那台出過一次被植入程式的事件。所有人的記憶會放在這台上 | 你已拍板要搬。資料庫只綁本機埠不對外、加密金鑰換新、48 小時內每日備份回 kkvin，之後改成定期備份到別處 |
| 改到共用的網站設定檔 | 兩台機器的網站設定是所有專案共用一個檔，OwnMind 要加一段 | 改之前備份、先驗證再套用；設定檔有錯時網站程式會拒絕套用並繼續跑舊設定，別的專案不會斷 |
| FAPA 共用 CI 檔是 Eric 管的 | 團隊規範（id=412）明寫 `ci/` 與主流程檔只有 Eric 能動，Vin 也不行 | 走規範設計的自動登記流程，共用檔全程由機器人與 Eric 經手，我們不碰 |
| 舊位址的相容 | 還沒升級的人繼續打 kkvin | 2-6 的轉送讓舊位址原封不動通到新伺服器，沒有相容問題；轉送會留到確認沒人在用 |
